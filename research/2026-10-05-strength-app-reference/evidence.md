## Source-confirmed distinctions

Kado README promises no app account, no subscription, no telemetry. Current Kado adds a paid one-time cosmetic Supporter Pack; its consumable tips still unlock nothing. Bob's tip-only/free-all-functionality direction should copy only the tip pattern and native stack, not the cosmetic paywall. Use new bundle/container/group/product IDs and support contacts. MIT permits adaptation provided notices accompany copied substantial portions. Branding/assets need their own provenance check before reuse.

Production always creates `.private(iCloud.dev.scastiel.kado)` CloudKit configuration. Despite README optional/opt-in language, no app-side switch is implemented; iOS Settings controls access. Production models use UUID attributes without uniqueness, optional inverse relationships, scalar sortOrder, primitive/data enum representations, and versioned lightweight migrations. Kado SyncHealth observes finished mirroring events; an available account plus unknown/healthy latest event produces "Syncing with iCloud." That is weaker than proof every record uploaded or restored.

The settings source exposes iCloud status, day/week start, appearance, notifications, archive, export/import, feedback/rating, tip jar and developer sandbox. No dedicated About/privacy/source/license screen was found. PRIVACY.md is dated April 19 and includes future HealthKit wording despite current README describing HealthKit as descoped; write a fresh privacy policy. No checked-in PrivacyInfo.xcprivacy was found in this source inventory. Review privacy manifests/required-reason APIs for the new app rather than treating Kado as compliance evidence.

Backup format is versioned independently from persistence schema. JSON/CSV import merges by UUID without deleting omitted objects, but existing fields are overwritten. Duplicate IDs can trap Dictionary(uniqueKeysWithValues); do not copy that as a journal integrity policy. SharedStore.swift contains stale widget comments contradicted by current README/CLAUDE: current widget architecture uses JSON snapshots and app intents reuse the main app live container. No widgets are necessary for the initial app.

Current floor is iOS18 in README, project settings and package. Package is swift-tools-version 6.0 and source uses newer concurrency syntax; README Swift5.10/Xcode16 minimum is not a verified current compatibility claim. Apple current stable table lists Xcode27 / Swift6.4. Recommend iOS18 deployment target, Swift6 language mode and a pinned stable toolchain validated on floor + current OS.

## Architecture conclusion and primary evidence

Automatic SwiftData CloudKit mirroring is a poor match for strict preservation of offline accepted workout history: an Apple Frameworks Engineer confirms iOS18-era mirroring can wipe locally saved, not-yet-uploaded changes when iCloud is disabled or the account signs out, by design. [Apple engineer response](https://developer.apple.com/forums/thread/811294). This is a technical reason to depart from Kado's mirroring rather than add a custom backend.

Use local-only authoritative SwiftData (`cloudKitDatabase: .none`), a single ModelActor writer, and CKSyncEngine private-database transport for immutable journal/config/rule events. Account-scoped durable outbox + serialized sync state + CKRecord system fields live locally. CKSyncEngine exists on iOS17+ and lets the app own persistence. [Apple approach comparison](https://developer.apple.com/documentation/cloudkit/deciding-whether-cloudkit-is-right-for-your-app), [CKSyncEngine](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5), [Apple sample](https://github.com/apple/sample-cloudkit-sync-engine).

Use a synchronous no-await transaction to validate expected revision, check ID/canonical-payload hash, insert event + update head + enqueue outbox together; disable autosave on this writer and rollback on failure. All mutations must go through the one actor, including imports and remote ingestion; never let views/extensions write directly. Apple documents transaction closure followed by save, but does not document it as general multi-context SQL CAS/isolation. Require actual concurrent writer, save failure, restart and process-interruption tests; a local SQLite transaction boundary is the fallback if the spike cannot prove the acceptance invariant. [ModelContext.transaction](https://developer.apple.com/documentation/swiftdata/modelcontext/transaction%28block%3A%29), [concurrency support](https://developer.apple.com/documentation/swiftdata/concurrencysupport), [SQLite atomic transactions in Apple guidance](https://developer.apple.com/documentation/xcode/reducing-disk-writes).

SwiftData uniqueness is UPSERT, not reject-on-duplicate. Preflight same ID/same hash as idempotent; same ID/different payload is an integrity conflict, never an automatic update. Restrict all writes to the actor to eliminate the preflight-insert race in a single process. [Apple SwiftData upsert description](https://developer.apple.com/videos/play/wwdc2024/10137/).

Cloud transport uses deterministic record names per immutable event ID (scoped by dataset/zone); duplicate same payload is idempotent, different payload quarantines. Transport unions immutable events but does not automatically linearize competing valid offline heads. Expected revision is local, not a globally serializable offline contract. Preserve causal parent IDs/branch evidence, block derived prescriptions on conflicts, require deterministic replay and explicit conflict resolution events. Do not sync mutable targets/caches as truth. Apple's earlier CloudKit talk illustrates immutable contributions/causal trees as a conflict strategy. [Using Core Data with CloudKit](https://developer.apple.com/videos/play/wwdc2019/202/).

Per-record `sentRecordZoneChanges.savedRecords` acknowledges successful server writes. Persist returned system fields and local acknowledgement durably; replay unacknowledged durable outbox after interruption. Deal separately with failedRecordSaves, quota/auth/schema errors, and serverRecordChanged. "Known pending upload count: 0 / last successful upload" is supportable; "everything permanently backed up" is not. Fresh-install hydration must replay only dependency-complete valid chains and visibly represent missing parents/unresolved branches. [SentRecordZoneChanges](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5/event/sentrecordzonechanges), [StateUpdate](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5/event/stateupdate).

Account transitions reset engine pending state. Preserve/segregate old-account local history and outbox; never automatically upload A history into B's cloud, or reuse A tokens/record system fields for B. Persist account/dataset ownership and require explicit migration/merge intent. Engine event delivery is serial; do not start send/fetch operations inside delegate callbacks. [AccountChange](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5/event/accountchange), [sign-in policy options](https://developer.apple.com/documentation/cloudkit/cksyncengineaccountchangetype/signin), [delegate event ordering](https://developer.apple.com/documentation/cloudkit/cksyncenginedelegate-1q7g8).

If automatic SwiftData mirroring were chosen instead, its schema cannot enforce uniqueness, requires optional inverse relationships and cannot depend on order/atomic relationship arrivals. CloudKit production schema evolution is additive; deployment to production is a release prerequisite, separate from app upload. These constraints also motivate stable versioned remote journal envelopes for custom sync. [SwiftData syncing constraints](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices), [TN3164 ordered-relationship/uniqueness limits](https://developer.apple.com/documentation/technotes/tn3164-debugging-the-synchronization-of-nspersistentcloudkitcontainer), [schema promotion](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema).

Private database content belongs to the iCloud user and is not visible to the developer via portal; it consumes the user's iCloud quota. No Sign in with Apple or app identity server is required. No telemetry means no app instrumentation/third-party collection, not that Apple platform services perform no processing. Provide truthful Apple transport/privacy disclosures and versioned file export/import independent of cloud. [privateCloudDatabase](https://developer.apple.com/documentation/cloudkit/ckcontainer/privateclouddatabase), [App privacy definitions](https://developer.apple.com/app-store/app-privacy-details/), [App Store platform analytics](https://developer.apple.com/app-store-connect/analytics/).

Recovery works only for successfully uploaded records in the same container/environment/account. Unsynced-device loss, user deletion, unavailable/changed account, quota and encrypted-key reset are limitations. Custom encrypted record payloads are supported but keychain reset can make old encrypted data permanently inaccessible; retain export and local preservation. [Encrypted fields/recovery limits](https://developer.apple.com/documentation/cloudkit/encrypting-user-data). Do not claim cloud sync as a historical independent backup or guarantee all data survives device loss.

## Tip implementation

Use own consumable StoreKit2 product IDs, localized Product.displayName/displayPrice, purchase success/cancel/pending/error/verification states, a launch-lived Transaction.updates listener plus unfinished reconciliation. Finish handled verified tip transactions, never unlock features, and never block training when App Store products cannot load. Kado additionally finishes unverified transactions because tips unlock nothing; treat that as its business-model choice, not a general entitlement pattern.

Consumable tips confer no restorable entitlement, so no Restore Tips is needed. Current iOS18+ can optionally return finished consumable history via SKIncludeConsumableInAppPurchaseHistory, but that is transaction history, not restoring a tip benefit; no need to opt in or build a server for the proposed jar. [currentEntitlements excludes consumables](https://developer.apple.com/documentation/storekit/transaction/currententitlements), [consumable history key](https://developer.apple.com/documentation/bundleresources/information-property-list/skincludeconsumableinapppurchasehistory), [unfinished reconciliation](https://developer.apple.com/documentation/storekit/transaction/unfinished), [Review Guidelines 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase).

## Verification gates worth carrying into plan

- Pure-domain deterministic replay, expected revision rejection, same-ID/hash idempotency vs differing-payload rejection; no wall-clock-only conflict winners.
- On-disk migration, local transaction failure/rollback, restart/crash boundary, concurrent actor commands, import/remote replay idempotency, malicious/duplicate/truncated/newer-version backup validation.
- Two devices: offline divergent edits, duplicate/out-of-order record delivery, missing causal parents, interrupted upload/ack persistence, throttle/quota/auth failures; cold fresh install into same account and full replay.
- iCloud disable/sign-out/switch while offline and while uploads remain; old outbox never migrates to new account; account changes while app quit.
- StoreKit local config + sandbox/TestFlight product availability, success/cancel/pending/Ask-to-Buy, interruption, duplicate finish handling, offline tip failure does not affect training.
- iOS18 floor/current OS, VoiceOver/Dynamic Type, stable toolchain CI unit/build/UI gates. No iOS CI copied from Kado since none was found.
- Production CloudKit schema promotion and signed TestFlight two-device test precede launch; publishing/signing/payment/product creation remain future explicitly authorized actions.
